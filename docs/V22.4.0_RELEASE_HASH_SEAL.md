- V22.4.0.1隔离静态灰度检查、应用运行时和依赖环境；

- V22.4.0.5把灰度证据语义绑定到当前Commit、Python环境和合同源码集合。

## 灰度检查隔离

### 纯静态检查器

`scripts/check_release_contract.py`只能读取AST、源码文本、JSON政策和文件路径，禁止导入：

```text
src.*
FastAPI app
数据库模块
Agent模块
Worker模块
```

静态检查不会触发应用导入绑定，也不会让被检查应用参与修改检查对象。

### 最终Bundle运行测试

Manifest生成并通过Root Verifier后，工作流复制最终Bundle，并使用独立生产Python 3.11.9执行：

```text
AI_RELEASE_REQUIRED=1
AI_RELEASE_ROOT=<sealed bundle copy>
AI_RELEASE_MANIFEST=<sealed manifest>
PYTHONDONTWRITEBYTECODE=1
```

该测试要求：

```text
FastAPI真实导入成功
evidenceSemanticVerified == true
runtimeEnvironmentMatch == true
三类文件验证数量 == Manifest数量
所有额外文件计数 == 0
```

随后Root Verifier再次检查副本，证明应用导入没有改写签封内容。

## 三类文件身份

### `runtimeFiles`

正式运行代码、前端、配置、启动部署脚本、Root Verifier副本、`requirements.lock`、发布Policy和Manifest Schema。

### `attestedFiles`

测试源码、纯静态检查器、Python 3.6兼容检查器、Manifest生成器、GitHub Actions工作流和发布文档。它们不执行线上业务，但必须随Bundle交付。

### `testEvidenceFiles`

CI实际运行产生的灰度证据位于：

```text
release/attestation/
```

以下文件必须全部存在且非空：

```text
compile-syntax.log
static-contract.log
app-route-smoke.log
pytest.log
production-runtime-verification.json
attested-files.sha256
test-attestation.json
pip-freeze.txt
python-runtime.json
```

Root Verifier和应用Release Identity均重新计算：

```text
testRunHash = SHA256(
  sorted(evidencePath + NUL + evidenceFileSHA256)
)
```

`testRunHash`只能证明证据文件集合没有变化，不能单独证明这些证据属于当前Release。

## 灰度证据语义绑定

V22.4.0.5增加第二层验证：对证据内容本身进行硬编码交叉核验。

```text
test-attestation.schema == release.test-attestation.v1
test-attestation.sourceCommit == manifest.sourceCommit
grayPythonVersion == productionPythonVersion == 3.11.9
requiredEvidenceFiles == 固定最低证据集合
全部必需测试标记 == 固定期待值
production-runtime-verification.verified == true
production-runtime-verification.strictExtras == true
missing == mismatched == extras == []
production-runtime-verification.pipFreezeHash == manifest.pipFreezeHash
python-runtime.pipFreezeHash == manifest.pipFreezeHash
SHA256(pip-freeze.txt) == manifest.pipFreezeHash
attested-files.sha256 == manifest.attestedFiles的路径与Hash集合
```

验证通过时，Root Verifier和正式应用公开：

```text
evidenceSemanticVerified == true
```

### 为什么仅有Hash仍不够

旧证据可以被复制到新版本，再重新计算：

```text
证据文件SHA256
→ testRunHash
→ manifestHash
→ releaseHash
```

这些Hash在数学上可以全部自洽，但证据仍可能属于旧Commit、旧Python环境或旧合同源码。V22.4.0.5要求证据内的Commit、环境与源码摘要同时指向当前Manifest，因此“完整重新签Hash的旧证据”仍会被拒绝。

## 精确证明集合

Root Verifier和应用运行态要求：

```text
Manifest runtimeFiles == Policy runtimeGlobs实际集合
Manifest attestedFiles == Policy attestedGlobs实际集合
Manifest testEvidenceFiles == release/attestation实际集合
```

应用接口公开：

```text
extraRuntimeFileCount
extraAttestedFileCount
extraTestEvidenceFileCount
manifestRuntimeFileOutsidePolicyCount
manifestAttestedFileOutsidePolicyCount
manifestTestEvidenceFileMissingCount
```

任一计数不为0，签封身份失败。这既阻断已签封文件被改写，也阻断旧流程通过新增文件重新复活。

## 依赖与Python身份

- `requirements.txt`只引用`requirements.lock`；
- `requirements.lock`是生产唯一精确依赖合同；
- `requirements-dev.lock`是灰度环境依赖合同；
- `scripts/check_dependency_lock.py --strict`阻断缺包、版本漂移和未声明包；
- 正式CI环境和ECS应用统一使用Python`3.11.9`；
- ECS系统Python 3.6不运行FastAPI应用。

正式运行必须满足：

```text
runtimePythonVersion == buildPythonVersion == 3.11.9
runtimePipFreezeHash == pipFreezeHash
runtimeEnvironmentMatch == true
```

## Python 3.6引导层兼容合同

ECS系统Python 3.6只负责运行Root Verifier和部署清理辅助代码。`scripts/check_python36_bootstrap.py`使用Python 3.6语法规则解析独立Verifier和嵌入式清理代码，并拒绝引导层出现Python 3.6不支持的语法或API。

兼容检查结果进入真实`compile-syntax.log`，检查器源码本身属于`attestedFiles`。

## Root Verifier信任锚

```text
固定Verifier: /usr/local/sbin/ai-release-verifier
固定Hash: /etc/ai-ecommerce-assistant/release-verifier.sha256
```

普通业务Release不能轮换Root信任。显式轮换必须同时提供：

```text
AI_RELEASE_VERIFIER_ROTATE=1
AI_RELEASE_VERIFIER_EXPECTED_OLD_SHA256=<当前Root固定Hash>
```

旧Hash不一致、Root状态不完整、符号链接或候选字节在安装中变化，轮换失败并恢复原状态。

## Manifest结构硬约束

```text
runtimeFiles非空且唯一
attestedFiles非空且唯一
testEvidenceFiles非空且唯一
allowedEntrypoints非空且唯一
verificationContract必填
buildEnvironment.pythonVersion固定为3.11.9
```

`verificationContract`必须精确等于：

```json
{
  "hashAlgorithm": "sha256",
  "canonicalJson": "utf8_sorted_keys_compact",
  "extraRuntimeFileAllowed": false,
  "forbiddenPathAllowed": false,
  "dependencyLockRequired": true,
  "attestedFilesRequired": true,
  "testEvidenceFilesRequired": true
}
```

## 反篡改与旧覆盖复活测试

Artifact上传前，CI构造并要求拒绝：

```text
修改attestedFiles文件
修改testEvidenceFiles文件
新增src/legacy_runtime_overlay.py
新增tests/legacy_contract_overlay.py
新增release/attestation/legacy-gray-proof.log
修改候选Root Verifier并尝试普通安装
把证据sourceCommit改成其他版本并重新计算所有Hash
伪造attested-files.sha256并重新计算所有Hash
```

灰度测试同时证明新流程能运行、签封文件未被修改、旧覆盖层无法复活、旧证据不能冒充当前Release、普通应用不能改写Root信任。

## 文件职责

- `release/release-policy.json`：声明运行文件、证明文件、精确Python、Root信任规则、入口和删除墓碑；
- `release/release-manifest.schema.json`：Manifest结构、唯一性和三类文件合同；
- `scripts/check_release_contract.py`：纯静态发布合同；
- `scripts/check_python36_bootstrap.py`：Python 3.6引导层兼容合同；
- `scripts/check_dependency_lock.py`：依赖闭包与环境Hash；
- `scripts/generate_release_manifest.py`：验证证据底线和语义后生成签封Bundle；
- `scripts/release_verifier.py`：Python 3.6兼容、无应用依赖的唯一Root Verifier；
- `scripts/install_release_verifier.sh`：首次固定或显式Root授权轮换Verifier；
- `scripts/runtime_exclusivity_guard.sh`：撤销影子Service、游离进程和墓碑旧文件；
- `scripts/deploy_release.sh`：使用固定Verifier验证Bundle并完成原子切换；
- `scripts/start_server.sh`：Uvicorn启动前重复验证Manifest、Python和依赖Hash；
- `src/services/release_identity_service.py`：应用启动和API验证Policy、文件、证据语义与实时环境身份。

冗余的应用导入型Manifest验证脚本已删除，避免形成第二验证权威。

## MVP硬阻断

以下任一情况发生，部署或启动失败：

1. Manifest Hash或Release Hash不匹配；
2. 三类文件缺失、变化、额外出现或Policy范围不一致；
3. 必需灰度证据缺失、为空或`testRunHash`复算失败；
4. 证据Commit、Python、依赖Hash、测试标记或合同源码摘要不属于当前Release；
5. Manifest与Policy版本、入口、墓碑或验证合同不一致；
6. `forbiddenPaths`中的旧脚本、工作流、文档或Runtime文件恢复；
7. 生产依赖缺失、版本漂移或出现未声明包；
8. CI生产环境、ECS基础Python或应用虚拟环境不是精确`3.11.9`；
9. Python 3.6引导层兼容检查失败；
10. Root Verifier文件与Root固定Hash不一致；
11. 普通Release尝试轮换Root Verifier；
12. 最终Bundle不能以`AI_RELEASE_REQUIRED=1`真实导入；
13. `evidenceSemanticVerified`不是`true`；
14. API与Worker Release Hash不同；
15. 除正式Service外仍有同仓库活动Service或游离进程；
16. SQLite一致性备份失败。

## MVP边界

本版本暂不加入Merkle Tree、Ed25519发布签名、蓝绿双实例或每任务Generation Lock。当前目标是在低配置ECS上，以轻量文件Hash、语义证据绑定、环境Hash和Root信任锚关闭代码漂移、证明缺失、跨版本证据复用、环境漂移、信任漂移和旧运行权复活。
