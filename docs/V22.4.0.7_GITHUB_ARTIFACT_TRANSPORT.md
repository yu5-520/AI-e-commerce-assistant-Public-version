# V22.4.0.7 / V22.5.2 — GitHub Artifact Transport for ECS

## Failures closed by this transport

The ECS deployment path previously depended on `git fetch origin main`. A temporary or regional timeout to `github.com:443` stopped deployment before dependency installation and left the server on the previous commit.

A second failure appeared after pull-request validation and release sealing shared the same workflow job. GitHub pull-request runs can build a temporary merge commit while the Artifact metadata still exposes the pull-request head SHA. That produced an invalid identity pair:

```text
workflow_run.head_sha != release-manifest.sourceCommit
```

V22.5.2 separates validation from formal release sealing:

```text
pull_request
→ validate exact pull-request head
→ compile / static contract / route smoke / full pytest
→ no deployable release Artifact

push refs/heads/main
→ checkout exact github.sha
→ verify event=push, ref=refs/heads/main and HEAD=github.sha
→ generate sealed Manifest and test attestation for the same commit
→ upload release-<github.sha>
```

## Formal transport chain

```text
GitHub API exact main head or AI_RELEASE_SOURCE_COMMIT
→ exact 40-character main commit
→ unexpired Artifact named release-<exact commit>
→ workflow run metadata lookup
→ event == push
→ status == completed
→ conclusion == success
→ head_branch == main
→ workflow path == .github/workflows/release-hash-seal.yml
→ workflow_run.head_sha == requested commit
→ artifact ZIP digest check when GitHub provides digest
→ exactly one release-*.tar.gz
→ release-manifest.sourceCommit == requested commit
→ test-attestation.sourceCommit == requested commit
→ test-attestation.releaseEvent == push
→ test-attestation.releaseRef == refs/heads/main
→ test-attestation.releaseBranch == main
→ deployableArtifact == true
→ pullRequestMergeArtifact == false
→ root-pinned verifier installation/idempotence check
→ bundle-owned deploy_release.sh
→ Release Hash, dependency, Python, evidence and data-lineage verification
→ current symlink atomic switch
→ rollback on failure
```

## Hard boundaries

- The transport script never runs mutable Git deployment commands on ECS.
- A mutable branch working tree is never treated as a deployable release.
- Only a successful `push` run on `main` from `.github/workflows/release-hash-seal.yml` may produce a deployable Artifact.
- Pull-request runs perform validation only and cannot upload a release Artifact.
- `AI_RELEASE_BRANCH` is no longer a branch-deployment switch; production transport accepts only `main`.
- `AI_RELEASE_SOURCE_COMMIT` can pin one exact main commit. If omitted, the current main head is resolved through the GitHub API.
- The exact commit must already have a completed, unexpired `release-<commit>` Artifact. The transport fails instead of selecting an older release or a pull-request Artifact.
- The Actions artifact download uses `api.github.com`, so a timeout limited to Git transport on `github.com:443` does not automatically block deployment.
- The candidate bundle must contain its Manifest, test attestation, verifier installer and deployment controller.
- Workflow run SHA, Artifact SHA, Manifest `sourceCommit` and test-attestation `sourceCommit` must all be identical.
- Root verifier replacement remains prohibited unless the explicit root-trust rotation contract is supplied.
- Existing rollback, SQLite backup and data-lineage checks remain unchanged.

## ECS command after this release is installed

Deploy current sealed main:

```bash
sudo bash /opt/ai-ecommerce-assistant/current/scripts/deploy_github_artifact.sh
```

Deploy one exact sealed main commit:

```bash
sudo AI_RELEASE_SOURCE_COMMIT=<40-character-main-commit-sha> \
  bash /opt/ai-ecommerce-assistant/current/scripts/deploy_github_artifact.sh
```

For GitHub configurations that require authenticated Actions Artifact download, provide a fine-grained token with `Actions: read` only:

```bash
sudo AI_GITHUB_TOKEN='<token>' \
  bash /opt/ai-ecommerce-assistant/current/scripts/deploy_github_artifact.sh
```

The token is read from the process environment, is not written into the repository, is not printed by the script, and is not forwarded to the redirected Artifact object-storage host.

## Low-configuration ECS behavior

The transport uses Bash, curl, tar and the existing bootstrap Python. It does not build a release on the server, run the Agent pipeline, or hash the live database. Network calls use bounded connection/request timeouts, multiple attempts and increasing retry delays. Temporary files are created under `/tmp` and removed on exit.
